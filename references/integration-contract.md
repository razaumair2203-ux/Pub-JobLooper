# Joblooper integration contract

Joblooper is the owner of candidate truth and employer-facing application artefacts. Other tools may enrich decisions around that workflow, but they must not become parallel CV generators or parallel truth stores.

## One source, many consumers

There are four distinct layers:

1. **Candidate truth** — the active Joblooper data root under `truth/`. For the personal source repository this is `.joblooper/truth/`; for the public distribution it is the user's external Joblooper data directory. These approved records are the only candidate facts that may authorize generated claims.
2. **Generation contract** — Joblooper's matching, section-selection, wording-variant, gate, render and release logic. Candidate-specific section configuration is part of the governed Joblooper data root. Generic defaults live in `examples/starter/` and ship through the public mirror.
3. **Advisory consumers** — career-strategy, project, prospect or research tools may read a digest-bound Joblooper consumer packet and return recommendations, source locators, risk notes or a proposed application brief. They may not approve truth, add CV claims, mark a submission or render a final employer document.
4. **Application artefacts** — CV, cover letter, preview, DOCX/PDF and release manifest are generated by Joblooper from one current plan. No other repository may maintain a competing final CV for the same application.

The dependency direction is therefore:

`candidate evidence -> Joblooper truth -> match/evidence plan -> reviewed CV + letter -> approved build -> exact submitted package`

External strategy context can influence *selection decisions* only through an explicit handoff or reviewed feedback. It cannot flow backward into truth automatically.

## Consumer packet

Run:

```text
python tools/export_context.py
```

or write the same packet to a file with:

```text
python tools/export_context.py --output path/to/context.json
```

The command emits `joblooper.consumer-context.v1`. It is a read-only, derived snapshot containing the current approved profile, career records, boundaries, aliases, section policy, source metadata and truth fingerprints.

The packet is useful for another application that needs to:

- classify a target role or career lane;
- select relevant project/evidence locators;
- identify known gaps or disclosure constraints;
- prepare an advisory handoff to Joblooper;
- display a career profile without re-parsing private implementation files.

It is **not** a second authority. The packet must never be edited and imported as truth, treated as approval, or used to bypass Joblooper's generation/release gates. Consumers should retain the `truth_sha256` and `generation_truth_sha256` fields so stale context is detectable.

## Shared data root

Multiple local Joblooper installations may point at the same candidate data root with `JOBLOOPER_DATA_DIR`. This is the supported way for the private authored source and the public installable engine to operate on one person's approved truth without copying it into two repositories.

The public repository itself never contains personal truth. For a normal public installation the default runtime root is `~/.joblooper`; an explicit `JOBLOOPER_DATA_DIR` overrides it. For the personal authored source, `.joblooper/` remains the governed source unless explicitly configured otherwise.

One data root has one writer at a time. The existing writer lock protects concurrent mutations; consumers that only need context should use the read-only export above.

## Advisory handoff contract

An orchestrator may hand Joblooper:

- exact JD source/location and reference;
- proposed primary career lane and supporting hook;
- relevant project/evidence locators;
- eligibility questions or residual risks to inspect;
- suggestions about which approved evidence deserves emphasis;
- a request to review a proposed generation-policy change.

It must not hand Joblooper invented candidate facts, rewritten ownership, inferred credentials, fabricated metrics, or a pre-approved final CV. Any new factual evidence goes through Joblooper truth intake and review before it can affect generation.

## Artefact invariant

Every employer-facing format for one application must descend from the same current plan. Markdown/chat review, CV JSON, cover-letter content, DOCX, PDF and release manifest must not have independent prose pipelines. A formatting or rendering change may change presentation, not candidate facts or approved wording.

## Repository roles

- `Pvt-JobLooper`: authored engine source plus the owner's governed personal runtime; private only.
- `Pub-JobLooper`: sanitized generated distribution of the same engine and contracts; no personal runtime in Git.
- career/project orchestrators: advisory context and routing only; they reference Joblooper truth by digest/anchor/source locator rather than copying it.

Change reusable CV-generation behavior in Joblooper first. Propagate accepted engine/contract changes to `Pub-JobLooper` through the sanitized release process. Do not implement equivalent CV logic independently in an orchestrator.
