# Joblooper integration contract

Joblooper is the owner of candidate truth, factual JD screening and employer-facing application artefacts. Other tools may enrich decisions around that workflow, but they must not become parallel gate engines, CV generators or truth stores.

## One source, many consumers

There are five distinct layers:

1. **Candidate truth** — the active Joblooper data root under `truth/`. For the personal source repository this is `.joblooper/truth/`; for the public distribution it is the user's external Joblooper data directory. These approved records are the only candidate facts that may authorize generated claims.
2. **Factual JD screen** — one complete advert is parsed and matched by Joblooper before application state exists. The screen owns exact requirement extraction, hard-gate classification, evidence mapping and unresolved factual gaps. It is read-only: screening must not create `work/` state, application events, CV records or approval state.
3. **Generation contract** — Joblooper's matching, section-selection, wording-variant, gate, render and release logic. Section order/caps are generation policy: changing them invalidates generation fingerprints and application plans, but does not require the candidate to re-attest unrelated career facts. Generic defaults live in `examples/starter/` and ship through the generated public release.
4. **Advisory consumers** — career-strategy, project, prospect or research tools may read a verified Joblooper consumer packet and/or factual JD-screen packet and return prioritization, route, positioning, source locators or strategy notes. They may not reclassify requirements, approve truth, add CV claims, mark a submission or render a final employer document.
5. **Application artefacts** — after an explicit pursue decision, the same verified factual screen is promoted into Joblooper application state. CV, cover letter, preview, DOCX/PDF and release manifest are generated by Joblooper from one current plan. No other repository may maintain a competing final CV for the same application.

The dependency direction is therefore:

`candidate evidence -> Joblooper truth -> one exact JD -> read-only factual screen -> career strategy -> explicit pursue -> promote same screen -> preflight/plan -> reviewed CV + letter -> approved build -> exact submitted package`

External strategy context can influence *selection decisions* only through an explicit advisory handoff. It cannot flow backward into truth or factual requirement classifications automatically.

Model/chat memory is outside this authority chain. It may help a consumer identify a repository, anchor candidate or verification question, but it cannot provide the missing factual source for a generated claim. Likewise, a repository commit/README may trigger truth intake but cannot enter an employer-facing document until the resulting candidate fact is approved.

## Factual JD screen

Use the dedicated screen command for exploratory opportunities rather than normal application ingestion:

```text
python tools/jd_screen.py screen jd.txt --company "Employer" --title "Role" --complete-advert --output screen.json
python tools/jd_screen.py verify screen.json --current
```

The screen emits `joblooper.jd-screen.v1`. `--complete-advert` is an explicit source assertion: a search snippet, partial vacancy card or inaccessible employer page must not be silently treated as an authoritative JD. If completeness cannot be established, factual screening is refused.

A screen contains:

- exact advert text plus byte-exact and normalized advert digests;
- the structured JD produced by the existing Joblooper parser;
- the existing deterministic identity and requirement classifications (`DIRECT`, `TRANSFERABLE`, `PARTIAL`, `GAP`, `BEHAVIOURAL`);
- evidence locators and exact parser-derived requirement wording;
- hard-gate and mandatory-risk summaries;
- candidate-truth approval and generation fingerprints;
- a stable factual `screen_sha256` plus full transport `packet_sha256`.

Do not create a second `UNRESOLVED` match taxonomy. A factual hard gate is unresolved when Joblooper marks `hard_gate=true` and its evidence classification is not `DIRECT`. Strategy tools may discuss the consequence but may not change the classification.

`truth_sha256` is retained as broad provenance, but audit-only changelog history is deliberately excluded from the stable screen identity/currentness gate. Currentness is bound to generation-relevant truth, the exact approved candidate-truth subject and the relevant engine/policy fingerprints. An audit note must not invalidate an otherwise identical factual screen.

The packet digests are integrity checks, not digital signatures. A party able to rewrite a packet can also recompute a non-secret digest. Therefore **promotion never trusts packet classifications merely because the hashes are internally consistent**: Joblooper recomputes the deterministic analysis from the embedded structured JD and current approved truth before creating application state.

### Promotion is the application boundary

When the user decides to pursue the opportunity:

```text
python tools/jd_screen.py promote screen.json
```

Promotion must:

1. verify packet integrity;
2. require current approved candidate truth;
3. require current generation/screen-engine bindings;
4. recompute the factual match from the embedded structured JD;
5. copy the exact embedded advert bytes into normal Joblooper work state;
6. record the source screen digest in application lineage;
7. initialize the normal advert-confirmation/preflight lifecycle.

It must **not** fetch or parse a different copy of the vacancy during promotion. Repeated promotion of the same exact screen is idempotent. A different advert using the same company/reference must not overwrite the existing application.

The second advert-confirmation gate after promotion remains intentional: the exploratory screen establishes source completeness and factual analysis; the application confirmation establishes that this exact captured employer/title record is the one the user is proceeding with before preflight and generation.

## Consumer packet

Run:

```text
python tools/export_context.py
```

or write the same packet to a file with:

```text
python tools/export_context.py --output path/to/context.json
```

The command emits `joblooper.consumer-context.v2`. The default `career-routing` scope is deliberately least-privilege: it excludes contact channels, external links, section/render policy, detailed source metadata and internal indices. Trusted local diagnostics may request the broader packet explicitly:

```text
python tools/export_context.py --scope full
```

Every v2 packet carries:

- exact truth and generation-truth fingerprints;
- the candidate-truth approval digest and review time;
- source repository identity and source revision when available;
- a digest of the complete transport payload (`packet_sha256`).

Consumers must recompute `packet_sha256` before trusting a saved or transported file. This detects accidental or stale-file mutation. It is an integrity check, not a cryptographic signature against a malicious party that can rewrite both payload and digest.

The packet is useful for another application that needs to:

- classify a target career lane at a strategic level;
- select relevant project/evidence locators;
- identify known disclosure constraints;
- prepare an advisory strategy handoff;
- display a bounded career profile without re-parsing private implementation files.

It is **not** a second authority. The packet must never be edited and imported as truth, treated as approval, or used to bypass Joblooper's screening/generation/release gates. A saved packet is a snapshot: unless the consumer directly invokes Joblooper at use time, currentness must be treated as unverified or checked against an explicit freshness threshold.

## Approval surfaces

Candidate truth approval and generation policy are intentionally separate.

Candidate sign-off binds facts and disclosure authority: profile facts, anchors, boundaries, aliases and reviewed sources. `truth/sections.json` is excluded from that candidate-attestation digest because it controls presentation rather than biography. It remains part of the generation fingerprint, so any section-policy change invalidates stale CV/application plans automatically.

A factual, source, wording or boundary change still requires renewed candidate sign-off where it changes the governed candidate-truth digest. A pure document-structure change requires a changed generation fingerprint and review of the resulting application plan, not re-attestation of unrelated facts.

## Shared data root

Multiple local Joblooper installations may point at the same candidate data root with `JOBLOOPER_DATA_DIR`, but only equivalent/current engine releases should be allowed to write it. The writer lock protects simultaneous mutations; it does **not** make an arbitrarily old engine data-schema compatible with a newer one.

Therefore:

- prefer one canonical writer (normally `Pvt-JobLooper` for the owner);
- treat other installs as read-only consumers unless they correspond to the same compatible generated release lineage;
- do not point an old public install at the governed data root merely because it starts successfully;
- use the v2 context export for advisory consumers that only need reads.

The public repository itself never contains personal truth. For a normal public installation the default runtime root is `~/.joblooper`; an explicit `JOBLOOPER_DATA_DIR` overrides it. For the personal authored source, `.joblooper/` remains the governed source unless explicitly configured otherwise.

## Career-strategy handoff contract

The normal user-facing workflow should not require the user to decide which subsystem to call. A natural request such as **“check this JD”** should route through the Joblooper factual screen and then expose the verified screen to the strategy layer.

A career orchestrator may return:

- opportunity priority or deprioritization;
- proposed primary career lane and supporting hook;
- direct-application, referral, networking or gate-clarification route;
- relevant project/evidence locators;
- strategic questions or residual risks;
- suggestions about which already-approved evidence deserves emphasis.

These are advisory outputs. The orchestrator must not:

- independently re-parse a valid screen into a competing gate verdict;
- change `DIRECT`/`TRANSFERABLE`/`PARTIAL`/`GAP` classifications;
- invent candidate facts, ownership, metrics, dates or credentials;
- mark an opportunity factually eligible, approved or submitted outside Joblooper;
- maintain a competing final-CV generation policy.

If an authoritative Joblooper screen is unavailable, the strategy layer may discuss the opportunity provisionally, but it must label factual eligibility as unverified and such provisional reasoning cannot be promoted into an application record.

Any genuinely new candidate evidence discovered by a strategy/project tool is a **pending evidence locator**, not candidate truth. It must pass Joblooper truth intake and review before it can affect a screen or generated document.

## Artefact invariant

Every employer-facing format for one application must descend from the same current plan. Markdown/chat review, CV JSON, cover-letter content, DOCX, PDF and release manifest must not have independent prose pipelines. A formatting or rendering change may change presentation, not candidate facts or approved wording.

The plan itself is compiled from the exact JD plus current approved atomic truth. There is no parallel chat-to-CV path: every factual rendered line must carry valid anchor provenance and survive the deterministic traceability/ownership/status/metric/boundary gates. An unsupported requirement remains an explicit gap or preflight question.

## Repository roles

- `Pvt-JobLooper`: authored engine source plus the owner's governed personal runtime; private only. It owns candidate truth, factual JD screening, application compilation and submission lineage.
- `Pub-JobLooper`: sanitized **generated release artifact** of the private engine; no personal runtime in Git and no independent feature-development line.
- career/project orchestrators: strategy and routing only; they consume verified Joblooper packets/evidence locators rather than copying authority.

A formal public export records the exact private source commit, exporter fingerprint and public release fingerprint. Do not manually reconstruct a public feature release file-by-file. Change reusable screening/CV-generation behavior in Joblooper first, run the private checks, then generate the public release through the sanitized exporter.
